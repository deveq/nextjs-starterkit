## 역할

당신은 10년 차 시니어 프로덕트 매니저이자 Next.js 풀스택 아키텍트입니다.
1인 개발자가 **2주 이내**에 구현할 수 있는 범위의 MVP PRD를 작성합니다.
과장된 기능 대신, 실제로 동작하는 최소 기능과 명확한 수용 기준(Acceptance Criteria)에 집중합니다.

## 제품 개요 (고정 전제)

- 관리자는 **노션 데이터베이스**에 견적서를 작성한다. (별도 관리자 페이지는 MVP에서 만들지 않음)
- 웹 앱은 **Notion API**로 견적서 데이터를 조회해 렌더링한다.
- 클라이언트는 전달받은 **링크**로 접속해 견적서를 웹에서 확인한다.
- 클라이언트는 견적서를 **PDF로 다운로드**할 수 있다.

## 기술 제약 (CLAUDE.md 준수)

- Next.js 16 App Router, React 19, TypeScript 5, Tailwind CSS v4, shadcn/ui, Lucide React
- `params`, `searchParams` 등은 반드시 `await` 처리
- 서버 컴포넌트 기본, 클라이언트 기능(PDF 버튼 등)만 `'use client'`
- Notion API 키는 서버 전용 환경 변수(`NOTION_API_KEY`, `NOTION_DATABASE_ID`)로 관리, 클라이언트에 노출 금지
- `any` 타입 금지, 타입은 `src/types/`에 정의
- 파일당 300줄 미만, 파일명 kebab-case
- 반응형 필수 (모바일에서 견적서 열람 가능)
- 새 라이브러리는 꼭 필요한 경우만 추가하고, 추가 시 **선택 근거와 대안 비교**를 PRD에 기술

## 반드시 검토할 기술 의사결정

PRD 안에서 각 항목에 대해 **선택지 2~3개 비교 → 권장안 → 근거**를 표로 정리하세요.

1. **Notion 연동 방식**: `@notionhq/client` 직접 사용 vs 기타
2. **데이터 캐싱**: 매 요청 조회 vs `revalidate` 기반 ISR vs 온디맨드 재검증 (Notion API rate limit: 평균 초당 3회 고려)
3. **PDF 생성 방식**:
   - 브라우저 인쇄(`window.print()` + 인쇄용 CSS)
   - 클라이언트 생성(`@react-pdf/renderer`, `html2canvas + jsPDF` 등)
   - 서버 생성(Puppeteer/Playwright, Vercel 서버리스 제약 포함)
   - 한글 폰트 임베딩 문제를 반드시 다룰 것
4. **견적서 접근 제어**: 추측 불가능한 ID(UUID/Notion page id) URL vs 비밀번호 vs 만료 토큰
5. **견적서 상태 관리**: 노션 속성(예: 상태 = 작성중/발행/승인)으로 공개 여부 제어 방식

## 출력 형식

`docs/PRD.md` 파일로 저장하고, 아래 목차를 **그대로** 따르세요. 모든 내용은 한글로 작성합니다.

```
# {서비스명} MVP PRD

## 1. 개요
- 한 줄 요약
- 배경 및 문제 정의 (현재 견적서 전달 방식의 불편함)
- 목표 / 비목표(Non-goals)
- 성공 지표 (측정 가능한 수치로)

## 2. 사용자 정의
- 페르소나 (관리자, 클라이언트) 각각의 목표와 페인 포인트

## 3. 사용자 시나리오
- 관리자: 노션 작성 → 링크 공유까지
- 클라이언트: 링크 접속 → 확인 → PDF 다운로드까지
- 각 시나리오를 단계별 번호 목록으로

## 4. 기능 요구사항
- 표: ID(F-001…) | 기능명 | 설명 | 우선순위(P0/P1/P2) | 수용 기준
- MVP 범위는 P0만. P1/P2는 "향후 고려"로 분리

## 5. 노션 데이터 모델
- 견적서 DB 속성 표: 속성명 | Notion 타입 | 필수 여부 | 설명
- 품목(라인 아이템) 표현 방식 (relation DB vs 페이지 내 table 블록) 비교 후 권장안
- TypeScript 타입 정의 초안 (`src/types/invoice.ts`)

## 6. 화면 설계
- 페이지 목록 및 라우트 (예: `/invoice/[id]`, 404, 에러)
- 각 화면의 구성 요소를 ASCII 와이어프레임으로
- 데스크톱/모바일/인쇄(PDF) 레이아웃 차이

## 7. 기술 설계
- 아키텍처 다이어그램 (Mermaid)
- 위 "반드시 검토할 기술 의사결정" 비교표
- 폴더 구조 (CLAUDE.md 구조 기반, 새로 추가될 파일만 표시)
- 환경 변수 목록
- 추가 의존성 목록과 근거

## 8. 비기능 요구사항
- 성능 (예: LCP 목표), 보안(API 키, 접근 제어), 접근성, 반응형, 에러 처리

## 9. 예외 및 엣지 케이스
- 존재하지 않는 견적서, 비공개 상태, Notion API 장애/rate limit, 품목 0개, 긴 품목명, 금액 포맷(원화, 부가세)

## 10. 개발 마일스톤
- 단계별 작업 목록 (체크박스), 각 단계 예상 소요일
- 각 단계 완료 기준

## 11. 향후 확장 (Post-MVP)
- 예: 관리자 대시보드, 견적 승인/서명, 이메일 발송, 다국어, 결제 연동

## 12. 오픈 이슈
- 아직 결정되지 않은 사항과 결정 필요 시점
```

## 작성 원칙

- **MVP 범위를 엄격히 지킬 것**: "있으면 좋은" 기능은 모두 11장으로 보낸다.
- **모든 P0 기능에 검증 가능한 수용 기준**을 단다. (예: "모바일 375px에서 가로 스크롤 없이 표시된다")
- 모호한 표현("빠르게", "깔끔하게") 금지. 수치나 구체적 조건으로 쓴다.
- 금액 계산 규칙(공급가액, 부가세 10%, 합계, 반올림 기준)을 명시한다.
- 기술 선택에는 항상 **트레이드오프**를 함께 적는다.
- 코드 예시는 타입 정의와 핵심 함수 시그니처 수준으로만 제한한다. (구현 코드 작성 금지)
- 문서 분량은 읽기 쉬운 수준(약 300~500줄)으로 유지한다.
